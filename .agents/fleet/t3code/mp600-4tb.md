# T3 Code on `mp600-4tb`

Last verified: 2026-08-11.

## Model

This personal Ubuntu desktop runs T3 Code directly as the normal `nei` user. It does not use the dedicated-user isolation used on `cron-data3`. T3 Connect exposes the instance through `app.t3.codes`; the application listener remains on loopback, and no inbound application port is open.

T3 Code and its agents have the same filesystem and command privileges as `nei`. Do not share this instance or its T3 Connect authorization.

## Access

For normal remote use, sign in to [app.t3.codes](https://app.t3.codes) as `nei.neto@hotmail.com` and select the `mp600-4tb` environment.

## Service

The supported T3 background-service installer created and enabled a user systemd unit. Linger is enabled for `nei`, so the service starts at boot and continues without an interactive login.

```sh
systemctl --user status t3code.service
systemctl --user restart t3code.service
systemctl --user stop t3code.service

t3 service status
t3 connect status
```

Logs are available from both locations:

```sh
journalctl --user -u t3code.service -n 200 --no-pager
tail -n 200 ~/.t3/userdata/logs/boot-service.log
```

Local verification:

```sh
curl --max-time 15 --fail --silent \
  http://127.0.0.1:3773/.well-known/t3/environment | jq
```

The response must identify `mp600-4tb`, report the expected T3 version, and return HTTP 200. A running instance also has one managed Cloudflared process for T3 Connect.

## T3 Connect

T3 Connect is authorized, exposure is enabled, the environment link is provisioned, and the managed relay tunnel starts with T3 Code.

```sh
t3 connect status
```

Expected essential state:

```text
Exposure: enabled
Authorization: stored credential
Environment link: provisioned
Relay: https://relay.t3.codes
```

The Cloudflared log can warn that its optional ICMP proxy is disabled because of `ping_group_range`. This does not affect the HTTPS/WebSocket tunnel used by T3 Connect and does not require a sudo change.

If authorization must be replaced:

```sh
t3 connect logout
t3 connect link --headless
systemctl --user restart t3code.service
t3 connect status
```

Treat the browser authorization code and all files under T3's credential/state directories as secrets. Do not paste them into logs or commit them.

## Installation and updates

Node is installed in the home directory, separately from Ubuntu's older `/usr/bin/node`. The stable selector is `~/.local/opt/node-v24`, and `node`, `npm`, `npx`, and `corepack` in `~/.local/bin` point through it.

Global npm packages must remain under `~/.local`:

```sh
export PATH="$HOME/.local/bin:$PATH"
export NPM_CONFIG_PREFIX="$HOME/.local"
```

The npm user configuration permits the required `node-pty` and `msgpackr-extract` install scripts. Keep this setting when reinstalling T3; without `node-pty`, agent terminals can fail.

Use T3's service updater after installing a tested release:

```sh
export PATH="$HOME/.local/bin:$PATH"
export NPM_CONFIG_PREFIX="$HOME/.local"

npm install --global --no-audit --no-fund t3@VERSION
t3 service update
systemctl --user restart t3code.service
```

Then verify the service, listener, T3 Connect, Codex, GitHub, Docker, and the registered project.

## Maintenance rules

- Keep the listener on `127.0.0.1:3773`; use T3 Connect for remote access.
- Run installation and maintenance commands as `nei`, not with `sudo`.
- Keep Node and npm-installed tools under `~/.local`.
- Do not delete the previous Node version until T3 Code, Codex sessions, and T3 Connect work after restart.
- Back up `~/.t3` only to an encrypted destination because it contains state and credentials.
- After any upgrade, restart the service and confirm that `t3 connect status` still reports a provisioned environment link.
